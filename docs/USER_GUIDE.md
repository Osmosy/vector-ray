# Руководство пользователя Vector Ray-Offline

Локальный движок симуляции общественного мнения. Вы загружаете документ — пресс-релиз, законопроект, аналитический отчёт — и получаете сотни ИИ-агентов с разными характерами, которые обсуждают этот документ в имитации соцсети: постят, спорят, меняют мнение. Затем система собирает отчёт и позволяет поговорить с любым агентом.

Всё работает на вашей машине. Ни один байт не уходит в облака: языковая модель — Ollama, граф знаний — Neo4j, интерфейс и промпты — на русском.

---

## 1. Что понадобится

| Компонент | Минимум | Рекомендуется |
|---|---|---|
| ОЗУ | 16 ГБ | 32 ГБ |
| Видеопамять (GPU) | 10 ГБ (модель 14b) | 24 ГБ (модель 32b) |
| Диск | 20 ГБ | 50 ГБ |
| Процессор | 4 ядра | 8+ ядер |

Без GPU всё работает, но генерация идёт заметно медленнее. Для слабых машин берите модель поменьше — `qwen2.5:7b` или `qwen2.5:14b`.

Что должно быть установлено:

- **Ollama** — локальный сервер моделей (обязательно, ставится на хост);
- **Docker + Docker Compose** — рекомендуется, либо вместо него Python 3.11+, Node.js 18+, Neo4j 5.18 и Ollama вручную;
- **Git** — чтобы склонировать репозиторий.

## 2. Запуск в Docker (проще всего)

### Шаг 1. Клонировать и подготовить конфигурацию

```bash
git clone https://github.com/Osmosy/vector-ray.git
cd vector-ray
cp .env.example .env
```

### Шаг 2. Отредактировать `.env` под Docker

В контейнере `localhost` — это сам контейнер, а Ollama живёт на вашем хосте. Поэтому адреса Ollama указываются через `host.docker.internal`, а пароль Neo4j должен совпадать с тем, который задаёт `docker-compose.yml` (`neo4j/vectorray123`):

```env
LLM_API_KEY=ollama
LLM_BASE_URL=http://host.docker.internal:11434/v1
LLM_MODEL_NAME=qwen2.5:14b

NEO4J_URI=bolt://neo4j:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=vectorray123

EMBEDDING_MODEL=nomic-embed-text
EMBEDDING_BASE_URL=http://host.docker.internal:11434

OPENAI_API_KEY=ollama
OPENAI_API_BASE_URL=http://host.docker.internal:11434/v1
```

`LLM_MODEL_NAME` — та модель, которую вы реально скачали (см. шаг 3).

### Шаг 3. Скачать модели в Ollama

Ollama должен быть запущен **на хосте**, отдельного контейнера с Ollama в compose нет:

```bash
ollama pull qwen2.5:14b        # языковая модель (32b — если хватает видеопамяти)
ollama pull nomic-embed-text   # эмбеддинги для векторного поиска, 768 измерений
```

### Шаг 4. Поднять стек

```bash
docker compose up -d
docker compose ps          # оба контейнера должны быть Up (healthy)
```

Поднимаются два контейнера: `vector-ray-offline` (интерфейс и API) и `vector-ray-neo4j` (база графа).

### Шаг 5. Открыть интерфейс

- приложение — **http://localhost:3000**
- Neo4j Browser (проверить, что база жива) — **http://localhost:7474**

Первая сборка образа занимает несколько минут: ставятся Python- и Node-зависимости.

## 3. Запуск без Docker

### 1. Neo4j

```bash
docker run -d --name vecneo4j \
  -p 7474:7474 -p 7687:7687 \
  -e NEO4J_AUTH=neo4j/vectorray123 \
  -e NEO4J_PLUGINS='["apoc"]' \
  neo4j:5.18-community
```

Пароль здесь и в `NEO4J_PASSWORD` в `.env` должны совпадать.

### 2. Ollama и модели

```bash
ollama serve &
ollama pull qwen2.5:14b
ollama pull nomic-embed-text
```

### 3. Бэкенд и фронтенд

Самый короткий путь — скрипты из корня проекта:

```bash
cp .env.example .env
# в .env оставьте localhost-адреса Ollama и пароль neo4j/vectorray123
npm run setup:all      # npm install в корне и во frontend + uv sync в backend
npm run dev            # одновременно бэкенд (:5001) и фронтенд (:3000)
```

Если `uv` не установлен, бэкенд можно поднять классически:

```bash
cd backend
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python run.py          # слушает 0.0.0.0:5001
```

Фронтенд отдельно: `cd frontend && npm install && npm run dev`.

Интерфейс — http://localhost:3000, API — http://localhost:5001 (фронтенд проксирует `/api` на него).

## 4. Настройка `.env`

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `LLM_API_KEY` | `ollama` | ключ LLM-провайдера; для Ollama подходит любое непустое значение |
| `LLM_BASE_URL` | `http://localhost:11434/v1` | адрес OpenAI-совместимого API |
| `LLM_MODEL_NAME` | `qwen2.5:32b` | имя модели; должна быть скачана |
| `EMBEDDING_MODEL` | `nomic-embed-text` | модель эмбеддингов (768 измерений) |
| `EMBEDDING_BASE_URL` | `http://localhost:11434` | адрес embedding-эндпоинта |
| `NEO4J_URI` / `NEO4J_USER` / `NEO4J_PASSWORD` | `bolt://localhost:7687` / `neo4j` / `vectorray123` | доступ к графу знаний; пароль обязан совпадать с базой |
| `OPENAI_API_KEY` / `OPENAI_API_BASE_URL` | как `LLM_*` | их читает движок симуляции OASIS |
| `OASIS_DEFAULT_MAX_ROUNDS` | `10` | раундов симуляции по умолчанию |
| `VECTOR_RAY_MAX_AGENTS` | — | ограничение числа агентов (меньше — быстрее) |
| `VECTOR_RAY_MINUTES_PER_ROUND` | — | сколько «минут реальности» в одном раунде |
| `VECTOR_RAY_TEST_MODE` | — | тестовый режим: быстрый прогон на малом объёме |
| `REPORT_AGENT_TEMPERATURE` | `0.5` | «свобода» формулировок в отчёте |
| `REPORT_AGENT_MAX_TOOL_CALLS` | `5` | сколько обращений к графу делает агент отчёта |
| `REPORT_AGENT_MAX_REFLECTION_ROUNDS` | `2` | глубина самопроверки при написании секций |
| `FLASK_DEBUG` | `False` | не включайте на машине, доступной по сети: бэкенд слушает `0.0.0.0`, и отладчик даёт консоль любому, кто дотянется до порта |

### Облачная модель вместо локальной

Локальный прогон упирается в железо: сотни агентов, каждый ход каждого агента — это запрос к модели, и на одной видеокарте симуляция занимает её целиком на часы. Если машина не тянет, рассуждения отдают облачному провайдеру: код общается с моделью по OpenAI-совместимому API, поэтому меняются три переменные.

```env
LLM_API_KEY=sk-...                          # ключ провайдера
LLM_BASE_URL=https://api.провайдер.ру/v1     # OpenAI-совместимый адрес
LLM_MODEL_NAME=имя-модели-у-провайдера
```

В Docker адрес провайдера указывается как есть — он внешний, `host.docker.internal` для него не нужен.

Что важно знать до переключения:

- **Эмбеддинги остаются локальными.** `EmbeddingService` обращается к Ollama по `/api/embed` и даёт 768-мерные векторы, поэтому Ollama с `nomic-embed-text` нужна в любом режиме. Сменить модель эмбеддингов нельзя «на лету»: другая размерность — и уже построенные графы несопоставимы с новыми.
- **Наружу уходят текст документа, промпты и ответы модели.** Локальный режим не отправляет ничего. Для внутренних документов оставайтесь на Ollama.
- **Нужен JSON-режим** (`response_format: json_object`): на нём держится разбор онтологии и конфигурации симуляции. Модели без поддержки JSON-режима дадут ошибку разбора, а не тихо испорченный результат.
- **Контекст — от 8k токенов.** Промпты длинные; модель с коротким окном обрежет вход и испортит результат.
- **Резервная цепочка моделей на облачном эндпоинте не работает**: она собрана из локальных имён Ollama, и подставлять их чужому API бессмысленно. Ошибка провайдера показывается как есть — так видно настоящую причину (неверный ключ, лимит, неизвестная модель).

Проверить связку до симуляции дешевле всего так: загрузить короткий документ, дойти до шага «Окружение» и посмотреть, генерируются ли персонажи. Если на этом шаге ошибка — дело в ключе, адресе или имени модели, а не в симуляции.

Часть настроек правится прямо в интерфейсе (раздел «Настройки»): форма пишет в `.env`. Часть значений читается при старте, поэтому после сохранения надёжнее перезапустить бэкенд.

## 5. Работа в интерфейсе

Слева-направо пять шагов; каждый следующий активен после успешного предыдущего.

### Шаг 1. Граф

1. Загрузите документ: PDF, Markdown или TXT, до 50 МБ. Лучше всего работает текст на 5–50 страниц с явными действующими лицами — компаниями, людьми, ведомствами.
2. Нажмите генерацию онтологии: система прочитает документ и предложит типы сущностей (например, «Компания», «Эксперт», «Регулятор») и типы связей.
3. Проверьте и при желании поправьте список типов — от него зависит, кого вообще увидит симуляция.
4. Запустите построение графа. Каждый фрагмент текста проходит через локальную модель: извлекаются сущности и связи, считаются эмбеддинги, всё пишется в Neo4j. Это самый долгий шаг: ориентируйтесь на несколько минут на каждые 10 страниц при 14b-модели на GPU.

### Шаг 2. Окружение

Система выбирает сущности из графа и генерирует для каждой персонажа: профессию, характер, склонность к риску, скорость реакции, влияние, память о прошлом. Затем собирает конфигурацию симуляции — стартовые посты, темы, тайминг.

Здесь же задаётся число раундов и число агентов. Начните с малого (20–40 агентов, 10–20 раундов), убедитесь, что всё работает, и только потом масштабируйте: время растёт примерно линейно.

### Шаг 3. Симуляция

Агенты общаются на двух площадках (Twitter- и Reddit-подобной): постят, отвечают, лайкают, цитируют. В интерфейсе видно ленту событий, распределение настроений и живой лог.

Симуляцию можно остановить и запустить заново. Если процесс упал, обработчик покажет ошибку и остановит опрос — интерфейс не будет бесконечно висеть в «идёт».

### Шаг 4. Отчёт

Агент отчёта анализирует результат: ищет в графе доказательства, проводит интервью с фокус-группой агентов, пишет секции по структуре (ключевые выводы, поведение групп, прогноз и риски). Готовый отчёт открывается в интерфейсе, его можно скачать и продолжить разговор по нему.

### Шаг 5. Взаимодействие

Чат с любым агентом симуляции: спросите, почему он написал именно это, что его переубедило бы, как он оценивает итог. Агент отвечает в своём характере и помнит собственные действия.

## 6. Где лежат данные

| Что | Где |
|---|---|
| загруженные документы и извлечённый текст | `backend/uploads/projects/<id>/` |
| состояние, персонажи и конфигурация симуляции | `backend/uploads/simulations/<sim_id>/` (`state.json`, профили, конфигурация) |
| отчёты и лог отчёта | `backend/uploads/reports/<report_id>/` |
| граф знаний | том Docker `neo4j_data` (или `data/` вашей Neo4j) |

Очистить всё — удалить каталоги внутри `backend/uploads` и выполнить в Neo4j Browser (`http://localhost:7474`) `MATCH (n) DETACH DELETE n`. Бэкап — копия `backend/uploads` плюс дамп базы Neo4j.

## 7. Если что-то не работает

| Симптом | Причина | Что делать |
|---|---|---|
| `Neo.ClientError.Security.Unauthorized` | пароль в `.env` не совпадает с базой | привести `NEO4J_PASSWORD` к паролю из `docker run`/compose (`vectorray123` по умолчанию) |
| «Нет связи с сервером» в логе | бэкенд не запущен или упал | `docker compose ps`, `docker compose logs vector-ray-offline`; в ручном режиме — консоль `python run.py` |
| `LLM_API_KEY не задан` | пустая переменная в `.env` | поставить любое непустое значение (для Ollama — `ollama`) |
| Ollama отвечает `connection refused` | сервер моделей не запущен или адрес из контейнера неверен | `ollama list` на хосте; в Docker — `host.docker.internal`, не `localhost` |
| модель не найдена | в `.env` указана модель, которой нет в Ollama | `ollama pull <имя>` или поправить `LLM_MODEL_NAME` |
| облако отвечает 401/403 | ключ неверный, без баланса или без доступа к модели | проверить `LLM_API_KEY` и имя модели в кабинете провайдера |
| облако отвечает `unknown model` | имя модели не то, что у провайдера | сверить `LLM_MODEL_NAME` со списком моделей провайдера (у Ollama и у облака имена разные) |
| облако отвечает `context length` | окно модели меньше промпта | взять модель с контекстом от 8k, уменьшить документ |
| отчёт получился пустым или «модель не ответила» при облаке | провайдер не поддерживает `response_format: json_object` | взять модель с JSON-режимом или вернуться на Ollama |
| пустой граф после построения | документ без явных действующих лиц, либо слишком крупные фрагменты | взять более «событийный» текст, уменьшить `DEFAULT_CHUNK_SIZE`, пересобрать граф |
| симуляция завершилась за секунды, действий ноль | окно симулированного времени попало в часы, когда у агентов не `active_hours` | прогон стартует с первого пикового часа конфигурации; если всё равно пусто — увеличьте `VECTOR_RAY_MINUTES_PER_ROUND` или число раундов. В `simulation.log` будет предупреждение |
| `Модель … не вернула текст: finish_reason=length` | модель-рассуждатель истратила весь лимит токенов на размышления | клиент один раз повторяет с утроенным лимитом; если и этого не хватило — возьмите модель без длинных рассуждений |
| всё очень медленно | модель велика для вашей видеопамяти, часть слоёв ушла на CPU | взять модель меньше (`7b`/`14b`), уменьшить число агентов и раундов, либо перейти на облачную модель (см. §4) |
| порт 3000 или 5001 занят | уже запущен другой экземпляр | остановить старый процесс или изменить порты в `docker-compose.yml` / `vite.config.js` |
| интерфейс открылся, но данные не грузятся | фронтенд поднят без прокси на API | запускать через `npm run dev` (прокси `/api` → `:5001`) или проверить `VITE_API_BASE_URL` |

Логи бэкенда: `docker compose logs -f vector-ray-offline` либо консоль `python run.py`. Лог каждого отчёта лежит рядом с отчётом в `backend/uploads/reports/`.

## 8. О чём помнить

- Качество симуляции определяется моделью. На 7b персонажи получаются плоскими, на 14–32b — заметно живее; отчёты на слабой модели стоит читать как черновик.
- Агенты — не предсказание будущего, а инструмент проверки гипотез: они показывают, какие линии реакции возможны, а не какая случится.
- Документ попадает в локальную модель целиком, поэтому не загружайте то, что нельзя обрабатывать на этой машине.
- Симуляция детерминирована лишь отчасти: один и тот же запуск даёт разные траектории — это нормально для стохастической модели.
